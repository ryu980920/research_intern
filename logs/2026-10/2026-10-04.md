# 2026-10-04 — ATLAS Code Flow Analysis

## 오늘의 목표

ATLAS에 새로운 방법을 제안하기 전에 현재 baseline 코드가 실제로 어떻게 동작하는지 확인한다.

특히 다음 연결을 이해하는 것이 목적이다.

**Design Parameter → SPICE → Metric → Feasibility/Surrogate → Next Candidate**

## 확인한 파일

- `run_experiment.py`
- `run_benchmark.py`
- `topbo/circuit_eval.py`
- `topbo/optimizers.py`
- `topbo/acquisition.py`
- `topbo/mapper.py`
- `eval_engines/ngspice/CircuitClass.py`
- `eval_engines/ngspice/ngspice_wrapper_parallel.py`
- `eval_engines/ngspice/ngspice_inputs/yaml_files/two_stage_opamp_gf180.yaml`
- TT two-stage op-amp netlist

상세 흐름은 `docs/atlas_code_flow.md`에 기록했다.

## Observation

### 1. Parameter가 실제 SPICE netlist에 들어가는 방식 확인

optimizer의 candidate vector가 YAML의 parameter 이름과 연결되고, wrapper가 netlist의 `.param` 값을 직접 치환한다.

### 2. 한 TT simulation에서 여러 분석이 함께 수행됨

- AC
- OP
- DC sweep
- Transient

각 결과는 CSV로 저장된 뒤 gain, UGBW, phase margin, bias current, output swing, settling time으로 변환된다.

### 3. ATLAS의 다음 candidate 선택 구조 확인

관측한 parameter/metric으로 surrogate를 학습하고, candidate pool을 만든 뒤 topology-aware acquisition으로 다음 design point를 선택한다.

### 4. PVT에 대한 중요한 차이 발견

YAML에는 TT 포함 17개의 corner netlist가 있지만, 현재 확인한 표준 runner는 `pvt=True`를 넘기지 않아 기본 실행은 TT-only이다.

반면 evaluator 내부의 PVT 기능을 켜면 TT soft gate 후 나머지 corner를 평가하고, 결과를 **metric별 worst-case 하나로 압축**해 반환한다.

## Interpretation

기존 smoke test의 metric을 “17-corner worst-case 결과”라고 보면 안 된다. 해당 실행은 기본 runner 기준 TT 결과다.

또한 robust PVT 연구에서는 단순히 corner 수가 많아 simulation cost가 증가한다는 사실뿐 아니라, **corner별 구조가 worst-case 압축 과정에서 사라지는지**를 실제 데이터로 확인할 필요가 있다.

## Research Implication

현재 코드에는 corner-wise PVT 정보를 생성할 기반은 있지만, optimizer가 사용하는 spec은 worst-case 형태로 압축된다.

이 구조는 향후 robust sizing 연구에서 다음 비교를 가능하게 한다.

```text
Worst-case compressed representation
vs.
Corner-wise representation
```

다만 이것이 실제 성능 개선으로 이어진다고 아직 결론 내리지 않는다. 먼저 baseline PVT 데이터를 확보해야 한다.

## Next

1. PVT mode를 안전하게 실행할 방법을 확인한다.
2. 하나 또는 소수의 design point부터 17-corner 결과를 수집한다.
3. corner별 metric table을 만든다.
4. metric별 worst-case가 어느 corner에서 발생하는지 확인한다.
5. corner-wise 정보를 유지할 필요가 실제로 있는지 판단한다.

## 추가 작업 — 새 PC 실행환경 구축 및 GF180 재현성 문제 확인

### 목적

새 컴퓨터에서도 기존 ATLAS 연구를 이어갈 수 있도록 실행환경을 구축하고, 동일한 design point를 반복 평가했을 때 같은 결과가 재현되는지 확인했다.

환경 구축 자체는 연구 결과가 아니므로 핵심 구성만 기록한다.

- WSL2 + Ubuntu 22.04
- Miniconda / Python 3.10
- Conda environment: `atlas`
- ATLAS repository: `youngmin0oh/atlas`
- ngspice 44.2
- GF180 primitive ngspice model
- `PDK_ROOT=$HOME/pdks`

### 문제 발견

ATLAS → ngspice → GF180 PDK → CSV → metric 추출 연결은 정상적으로 동작했다.

하지만 동일한 `init_params`와 동일한 TT netlist를 반복 실행했을 때 gain, phase margin, bias current, output swing 등이 매번 달라졌다.

Python wrapper를 제거하고 동일한 `.cir` 파일을 ngspice에서 직접 3회 실행해도 `ac.csv`, `dc.csv`, `dc_sweep.csv`, `tran.csv`의 SHA-256이 매번 달랐다.

따라서 문제는 ATLAS optimizer나 Python metric extraction이 아니라 **ngspice가 읽는 GF180 model 설정 쪽**으로 좁혀졌다.

### 원인 확인

GF180의 `design.ngspice`를 확인한 결과 statistical variation switch의 기본값이 다음과 같이 활성화되어 있었다.

```spice
sw_stat_global = 1
sw_stat_mismatch = 1
```

즉 nominal TT simulation을 의도했지만 실제로는 GF180 model 내부에서 **global process variation + local mismatch가 매 실행마다 랜덤하게 적용**되고 있었다.

개념적으로는 다음과 같았다.

```text
same design x + TT condition
→ random global variation + random mismatch
→ different virtual chip sample
→ different circuit metrics
```

OpenMP 영향도 확인하기 위해 single-thread 설정과 `--disable-openmp`로 별도 빌드한 ngspice 44.2를 시험했지만 결과는 여전히 매 실행마다 달랐다. 따라서 OpenMP가 주원인은 아니었다.

### 수정

로컬 GF180 `design.ngspice`의 statistical switch를 nominal simulation용으로 변경했다.

```spice
sw_stat_global = 0
sw_stat_mismatch = 0
```

원본은 로컬에서 `design.ngspice.bak`으로 백업했다.

### 수정 후 검증

동일 TT netlist를 ngspice로 3회 반복 실행한 결과 네 raw CSV의 SHA-256이 모두 동일했다.

```text
ac.csv        c47affe6ca1e74482a4f48600e0a90ebf88af841281c0f9e496b08a8e24b75a3
dc.csv        c2d263dff53ec7315f1631bd7e35672941cabffa29f376e933c68b4357f87d57
dc_sweep.csv  3338f3e03f17a21648763533eb690a1adafb0f61760aa13a24deaf1b18c342c0
tran.csv      d1cccae0d6d9b7e694a8352bc0583fed350a2c1794da8f52a632aa391d803f3d
```

ATLAS의 `CircuitEvaluator.evaluate_tt()`도 3회 반복 결과가 완전히 동일했다.

```text
gain_min      = 543.4600000000053
ibias_max     = 0.00055581049
phm_min       = 29.214151096544953
t_settle_max  = 1.6563499999999829e-06
ugbw_min      = 25927856.743177846
vswing_min    = 1.0206877
```

### Observation → Interpretation → Research Implication → Next

**Observation:** 동일 design point의 결과가 처음에는 반복 실행마다 달랐고, GF180 statistical switch를 끈 뒤 raw CSV와 metric이 모두 동일하게 재현됐다.

**Interpretation:** 초기 비결정성은 ATLAS 연결 실패가 아니라 GF180 PDK의 기본 statistical variation 설정 때문이었다.

**Research Implication:** PVT landscape를 분석할 때 Monte Carlo variation이 동시에 켜져 있으면 성능 변화가 corner 때문인지 random process/mismatch 때문인지 분리할 수 없다. 따라서 현재 PVT baseline 연구에서는 statistical variation을 끈 nominal model을 사용한다.

**Next:** nominal GF180 조건을 고정한 뒤 소수 design point에서 PVT evaluation을 시작하고, corner-wise metric을 보존한다.

## EXP-001 — init_params 첫 17-corner PVT baseline

GF180 statistical variation을 OFF한 deterministic 조건에서 YAML 기본 `init_params` 한 점을 TT 포함 17개 PVT corner에 처음으로 평가했다.

정식 실험 기록은 다음에 저장했다.

```text
experiments/EXP-001_pvt_init_params_baseline/
├─ README.md
├─ config/run_config.md
├─ scripts/evaluate_init_params_pvt.py
├─ data/corner_metrics.csv
└─ raw/README.md
```

### 핵심 결과

- 17개 corner 모두 simulation 및 metric extraction 성공
- feasible corner: 0 / 17
- 모든 corner에서 phase margin이 60 deg target 미달
- UGBW도 미달한 corner:
  - SS / 3.0 V / 125 C
  - SF / 3.0 V / 125 C
- metric별 worst corner가 서로 다름
  - Gain / Vswing: FF / 3.0 V / 125 C
  - Ibias: FF / 3.6 V / -40 C
  - Phase Margin: FS / 3.6 V / -40 C
  - Settling / UGBW: SS / 3.0 V / 125 C

### 해석

첫 design point에서도 metric별 worst corner가 하나로 일치하지 않았다. 따라서 PVT worst-case compression은 여러 실제 corner의 worst metric을 조합한 synthetic vector가 될 수 있다.

다만 design point가 하나뿐이므로 feasible island의 이동·분열·소멸은 아직 판단할 수 없다.

### 데이터 보존 상태

17-row corner-wise metric CSV는 보존했다.

이번 최초 실행에서는 wrapper가 temporary simulation directory를 삭제했기 때문에 17 corners x 4 analysis의 raw CSV(`ac.csv`, `dc.csv`, `dc_sweep.csv`, `tran.csv`)는 보존되지 않았다. 이 점을 EXP-001 limitation으로 명시했다.

다음 PVT dataset부터는 raw output 보존을 먼저 해결한 뒤 multi-design-point dataset을 생성한다.

## 후속 결정 — PVT 데이터 보존 정책 정리

EXP-001 직후에는 다음 multi-point PVT dataset부터 모든 corner의 raw output을 먼저 보존하는 방향을 고려했다.

이후 실제 연구 목적과 예상 파일 수를 다시 검토해 이 결정을 수정했다.

### 변경 이유

현재 feasible-region / feasible-island 분석에서 직접 사용하는 데이터는 각 design point의 **corner-wise metric과 feasibility table**이다. 모든 design point × 17 corners에 대해 `ac.csv`, `dc.csv`, `dc_sweep.csv`, `tran.csv`를 상시 저장하면 분석에 직접 필요하지 않은 파일이 빠르게 증가하고 실험 결과를 찾기 어려워진다.

따라서 현재 데이터 보존 원칙은 다음과 같이 정한다.

```text
항상 보존
→ experiment config
→ 실행 script
→ corner-wise metric / feasibility dataset
→ 결과 해석

선택적으로 보존
→ 이상 metric 원인 분석에 필요한 raw waveform
→ 파형 자체가 연구 근거가 되는 경우의 raw data
→ 실제 분석/발표에 필요한 figures
```

raw waveform이 필요한 경우에는 config와 code가 고정되어 있으므로 해당 design/corner만 재실행해 생성한다.

이에 따라 "다음 PVT dataset 전에 모든 raw output 보존부터 해결한다"는 이전 계획은 **superseded**되었으며, 다음 우선 작업은 **multi-design-point 17-corner metric dataset 생성**이다.

# 2026-10-04 — ATLAS Code Flow Analysis

## 오늘의 목표

ATLAS에 새로운 방법을 제안하기 전에 현재 baseline 코드가 실제로 어떻게 동작하는지 확인한다.

특히 다음 연결을 이해하는 것이 목적이다.

**Design Parameter → SPICE → Metric → Feasibility/Surrogate → Next Candidate**

## Observation

### 1. Parameter가 실제 SPICE netlist에 들어가는 방식 확인

optimizer의 candidate vector가 YAML의 parameter 이름과 연결되고, wrapper가 netlist의 `.param` 값을 직접 치환한다.

### 2. 한 TT simulation에서 여러 분석이 함께 수행됨

- AC
- OP
- DC sweep
- Transient

각 결과는 CSV로 저장된 뒤 gain, UGBW, phase margin, bias current, output swing, settling time으로 변환된다.

### 3. ATLAS의 다음 candidate 선택 구조 확인

관측한 parameter/metric으로 surrogate를 학습하고, candidate pool을 만든 뒤 topology-aware acquisition으로 다음 design point를 선택한다.

### 4. PVT에 대한 중요한 차이 발견

YAML에는 TT 포함 17개의 corner netlist가 있지만, 현재 확인한 표준 runner는 `pvt=True`를 넘기지 않아 기본 실행은 TT-only이다.

반면 evaluator 내부의 PVT 기능을 켜면 TT soft gate 후 나머지 corner를 평가하고, 결과를 **metric별 worst-case 하나로 압축**해 반환한다.

## Interpretation

기존 smoke test의 metric을 “17-corner worst-case 결과”라고 보면 안 된다. 해당 실행은 기본 runner 기준 TT 결과다.

또한 robust PVT 연구에서는 단순히 corner 수가 많아 simulation cost가 증가한다는 사실뿐 아니라, **corner별 구조가 worst-case 압축 과정에서 사라지는지**를 실제 데이터로 확인할 필요가 있다.

## Research Implication

현재 코드에는 corner-wise PVT 정보를 생성할 기반은 있지만, optimizer가 사용하는 spec은 worst-case 형태로 압축된다.

이 구조는 향후 robust sizing 연구에서 다음 비교를 가능하게 한다.

```text
Worst-case compressed representation
vs.
Corner-wise representation
```

다만 이것이 실제 성능 개선으로 이어진다고 아직 결론 내리지 않는다. 먼저 baseline PVT 데이터를 확보해야 한다.

# 2026-10-04 — PVT Baseline, EXP-001/002, and Execution Diagnostics

## 오늘의 목표

ATLAS의 실제 PVT 처리 방식을 코드와 simulation으로 확인하고, 현재 연구 질문인 **worst-case compression vs. corner-wise representation**을 검증할 첫 multi-design PVT dataset을 만든다.

---

## 1. ATLAS PVT Code Flow 확인

### 수행 작업

다음 흐름을 실제 코드 기준으로 추적했다.

```text
design parameter x
→ YAML parameter mapping
→ SPICE netlist .param replacement
→ ngspice AC / OP / DC sweep / transient
→ metric extraction
→ feasibility
→ surrogate / acquisition
→ next candidate
```

또한 기본 runner는 evaluator에 `pvt=True`를 주지 않으므로 일반 실행은 TT-only이고, evaluator 내부 PVT mode에서는 TT 이후 나머지 corner를 평가한 뒤 **metric-wise worst-case vector로 압축**함을 확인했다.

### 해석

17 corner netlist가 존재한다는 사실과 기본 ATLAS optimization이 17 corner를 사용하는 것은 같은 의미가 아니다.

현재 연구에서는 optimizer에 전달되기 전 사라지는 corner-wise 정보를 별도로 보존해야 한다.

## 2. GF180 Simulation Reproducibility 문제 확인

### 문제

동일 TT design point를 반복 실행했는데 metric과 raw output이 매번 달라졌다.

### 원인 확인

GF180 `design.ngspice`의 statistical setting이 기본적으로 활성화되어 있었다.

```spice
sw_stat_global = 1
sw_stat_mismatch = 1
```

즉 nominal TT evaluation이라고 생각했지만 실제로는 random global variation과 local mismatch가 같이 들어가고 있었다.

### 수정

PVT baseline에서는 다음처럼 변경했다.

```spice
sw_stat_global = 0
sw_stat_mismatch = 0
```

### 결과

동일 netlist 반복 실행에서 raw CSV hash와 metric이 동일하게 재현됨을 확인했다.

### Research implication

PVT 변화와 Monte Carlo variation을 동시에 섞으면 성능 변화의 원인을 구분할 수 없다.

따라서 현재 baseline 원칙은:

```text
PVT study
→ statistical variation OFF

Monte Carlo / mismatch study
→ 별도 실험에서 명시적으로 ON
```

## 3. EXP-001 — D000 17-Corner Baseline

### 목적

YAML `init_params` 한 점을 17 PVT corners에서 평가해 corner별 metric 차이와 worst-corner identity를 확인한다.

### 결과

- Design: D000
- PVT corners: 17
- Feasible: 0 / 17
- 모든 corner에서 phase margin < 60 deg
- UGBW도 일부 high-temperature / low-voltage corners에서 target 미달

metric별 주요 worst corner:

- Gain / Vswing → FF / 3.0 V / 125 C
- Ibias → FF / 3.6 V / -40 C
- Phase Margin → FS / 3.6 V / -40 C
- Settling / UGBW → SS / 3.0 V / 125 C

### 해석

하나의 design point에서도 metric별 worst corner가 서로 달랐다.

따라서 metric-wise worst-case compression은 실제 하나의 physical corner가 아니라 **서로 다른 corner의 worst metric을 합친 synthetic vector**가 될 수 있다.

다만 design point가 하나뿐이므로 feasible-island의 이동·분열·지속성은 판단할 수 없다.

## 4. PVT Data 저장 정책 정리

### 결정

현재 연구에서 항상 보존할 데이터:

```text
experiment config
execution script
design_points.csv
corner_metrics.csv
interpretation
```

모든 corner의 AC / DC / DC-sweep / transient raw CSV를 상시 보존하지 않는다.

raw waveform은 이상 metric 진단이나 파형 자체가 근거가 되는 특정 design/corner에서만 선택적으로 재생성한다.

### 이유

현재 연구 질문은 corner-wise feasible structure이므로 핵심 분석 데이터는 parameter와 metric table이다.

불필요한 raw 파일을 모두 저장하면 데이터 추적성이 오히려 떨어진다.

## 6. EXP-002 — ATLAS Initial 20-Point PVT Pilot

### 목적

임의 100 points를 먼저 평가하지 않고, ATLAS가 실제 optimization 시작 시 사용하는 initial design set을 먼저 확인한다.

ATLAS current default:

```text
n_init = 20

D000        : YAML init_params
D001-D012   : init_params 주변 local perturbation
D013-D019   : global LHS
```

D000은 EXP-001에서 이미 평가했으므로 EXP-002에서는 D001-D019만 추가했다.

### Attempt 1 — Import Failure

오류:

```text
ImportError: cannot import name 'ATLAS' from 'topbo.optimizers'
```

원인:

CLI method 이름은 ATLAS이지만 실제 Python class 이름은 `TopoBO`였다.

수정:

```python
from topbo.optimizers import TopoBO
atlas = TopoBO()
```

simulation 시작 전 오류였으므로 결과 데이터에는 영향이 없다.

## 7. D006 Timeout Diagnostic

### 문제

EXP-002에서 D001-D005 완료 후 D006의 다음 corner가 120 s timeout에 걸렸다.

```text
D006
FF_3.6V_m40C
ngspice timeout after 120 s
```

당시 나머지 16 PVT corners를 최대 8개 병렬 실행하고 있었다.

### 진단 실험

D006만 따로 17 corners를 순차 실행했다.

### 결과

- D006 17 / 17 simulation 완료
- 이전 timeout corner인 FF / 3.6 V / -40 C도 정상 완료
- diagnostic CSV 별도 저장

### 해석

D006 또는 해당 corner 자체가 본질적으로 simulation 불가능한 것은 아니다.

동일 조건이 sequential execution에서는 완료됐으므로, 병렬 실행 시 자원 경쟁 또는 wall-time 증가가 timeout에 영향을 줬을 가능성이 높아졌다.

한 번의 비교만으로 원인을 완전히 확정하지는 않는다.

### 결정

20-point pilot에서는 안정적인 dataset 확보를 우선해 **corner-wise sequential execution**으로 변경했다.

병렬도 최적화는 별도 성능 문제로 분리한다.

## 8. EXP-002 최종 결과

EXP-001 + EXP-002 통합:

```text
20 designs × 17 corners = 340 corner evaluations
```

### Feasibility

- Feasible evaluations: 0 / 340
- 하나 이상의 corner에서 feasible한 design: 0 / 20
- 17 corners 모두 feasible한 robust design: 0 / 20

### Spec failure frequency

한 evaluation이 여러 spec을 동시에 실패할 수 있다.

| Spec | Fail count | Fail rate |
|---|---:|---:|
| UGBW | 252 | 74.1% |
| Output swing | 238 | 70.0% |
| Gain | 218 | 64.1% |
| Phase margin | 208 | 61.2% |
| Settling time | 169 | 49.7% |
| Bias current | 29 | 8.5% |

### Near-feasible observations

D000, D007, D008, D009는 TT에서 6개 spec 중 **phase margin만 실패**했다.

반대로 phase margin이 충분히 높은 D002 / D006 계열은 gain, UGBW, output swing이 크게 부족했다.

이는 현재 design space에서 stability와 gain / bandwidth / swing 사이의 trade-off가 강함을 보여준다.

### Worst-corner frequency

주요 metric별 가장 자주 등장한 worst corner:

- Gain → FF / 3.0 V / 125 C: 15 / 20
- Ibias → FF / 3.6 V / -40 C: 18 / 20
- Phase margin → FS / 3.6 V / -40 C: 13 / 20
- UGBW → SS / 3.0 V / 125 C: 18 / 20

### Research implication

EXP-001에서 관찰한 **metric별 worst corner 불일치**가 20 designs에서도 반복됐다.

그러나 feasible point가 0개이므로 아직 feasible-island topology를 분석할 수 없다.

## 9. 다음 판단

다음 단계는 임의 100-point PVT sweep이 아니다.

Robust feasible design은 반드시 TT에서도 feasible해야 하므로 먼저 ATLAS adaptive search를 이용해 TT feasible 또는 near-feasible region을 찾는다.

```text
ATLAS initial 20 points
→ adaptive TT search
→ TT feasible / near-feasible candidates
→ selected candidates 17-corner PVT
→ corner-wise feasible-set comparison
→ feasible-island 분석 확대 판단
```

feasible / boundary point가 충분히 확보된 이후에만 50/100-point PVT dataset과 island topology 분석으로 확대한다.

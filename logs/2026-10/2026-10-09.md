## 1. Important Correction — standard runner의 n_init은 고정 20이 아님

이전 EXP-002는 `TopoBO.optimize(...)`의 함수 기본값인:

```python
n_init=20
```

을 기준으로 `N_INIT = 20`을 명시적으로 사용했다.

그러나 실제 standard entry point인 `run_experiment.py`는 optimizer를 호출할 때 다음 함수로 `n_init`을 다시 계산한다.

```python
def n_init_for(evaluator, budget):
    return max(min(3 * evaluator.n_params, budget // 3, 50), 10)
```

two-stage GF180 op-amp는 design parameter가 7개이므로:

```text
3 × 7 = 21
```

budget이 63 이상이면 standard runner의 initial sample 수는 **21**이 된다.

예:

```text
budget = 500
→ min(21, 166, 50)
→ n_init = 21
```

따라서 EXP-002의 20-point dataset은 **TopoBO optimizer default n_init=20을 사용한 pilot**이라고 표현해야 하며, 일반적인 `run_experiment.py` 실행의 initial set과 완전히 동일하다고 표현하면 안 된다.

### 의미

EXP-002 결과 자체는 잘못된 것이 아니다.

20개 design × 17 PVT 결과는 그대로 유효하다.

수정해야 하는 것은 **baseline을 설명하는 표현**이다.

- EXP-002: optimizer-default `n_init=20` pilot
- standard runner: budget과 parameter 수에 따라 `n_init_for()`로 결정
- 7-parameter op-amp + budget >= 63이면 21 initial points

## 2. Initial 이후 Adaptive Loop 확인

`_GPBasedOptimizer.optimize()` 기준으로 initial evaluation이 끝난 뒤 각 iteration에서 다음 순서가 수행된다.

```text
observed X / metrics
→ working constraints 설정
→ surrogate fit
→ 50,000 candidate pool 생성
→ surrogate가 candidate metrics / feasibility 예측
→ near-feasible set F_hat 구성
→ Mapper topology 분석
→ wEI + topology term 계산
→ 최고 score candidate 1개 선택
→ 그 1개만 SPICE simulation
→ observation에 추가
→ 반복
```

50,000 candidates를 모두 SPICE simulation하는 것이 아니다.

surrogate로 50,000개를 저비용 screening한 뒤 **선택된 1개만 실제 simulation**한다.

## 3. Candidate Pool

현재 코드:

```python
N_CANDIDATES = 50000
```

아직 feasible point가 없으면:

```text
80% global LHS = 40,000
20% local      = 10,000
```

으로 구성한다.

local candidates는 현재까지 관측한 design 중 multi-spec score가 높은 최대 5개를 anchor로 사용한다.

feasible point가 생긴 뒤에는 global fraction이 60%로 감소한다.

## 4. Near-Feasible Set and Topology

ATLAS는 실제 feasible observation이 아직 없어도 surrogate prediction으로 near-feasible set `F_hat`을 만든다.

기본적으로 50,000 candidate 중 predicted feasibility score `h`가 높은 상위 약 10–20%를 선택한다.

그 뒤 Mapper를 이용해 predicted near-feasible region의 component / topology를 분석하고 candidate의 bridge / frontier / interior 역할을 acquisition에 반영한다.

따라서:

```text
actual feasible sample이 0개
≠
ATLAS가 topology를 전혀 사용할 수 없음
```

이다.

다만 **실제 corner-wise feasible island를 실험 데이터로 검증하는 것**은 여전히 실제 feasible / boundary samples가 필요하다.

## 5. Current 20 TT Data에서 발견한 추가 관찰

현재 D000-D019 TT 결과를 코드의 bottleneck 계산 방식에 대입하면, 각 metric은 서로 다른 design에서 이미 target을 한 번 이상 만족한다.

예:

- 어떤 design은 gain이 매우 좋음
- 다른 design은 phase margin이 매우 좋음
- 또 다른 design은 current가 매우 좋음

하지만 **하나의 design이 6개 spec을 동시에 만족한 경우는 없음**이다.

현재 코드의 bottleneck-aware weighting은 metric별 `best observed value`를 전체 design에서 각각 따로 찾는다.

그 결과 첫 adaptive step에서 UGBW가 상대적으로 가장 큰 bottleneck weight를 받고, phase margin은 다른 design에서 높은 값이 이미 관측되었기 때문에 큰 bottleneck으로 보지 않는다.

반면 실제 near-feasible TT designs인 D000 / D007 / D008 / D009는 모두 **phase margin 하나 때문에 infeasible**하다.

### Interpretation

이 관찰은 흥미롭지만 아직 “ATLAS가 잘못됐다”고 결론 내릴 수 없다.

이유:

- bottleneck weighting은 acquisition의 일부일 뿐이다.
- `compute_h()`, probability of feasibility, Mapper topology는 여러 spec의 joint structure를 함께 본다.
- 실제 adaptive trajectory를 확인해야 이 weighting이 candidate selection에 어떤 영향을 주는지 판단할 수 있다.

따라서 다음 실험에서 확인할 핵심은:

> **D020 이후 adaptive candidates가 실제로 joint-feasible direction으로 이동하는가?**

이다.

## 7. EXP-003 실험 목적/설정 보강 (같은 날 후속 논의)

### 새로 명확해진 질문

EXP-003의 목표는 **ATLAS의 성능 자체를 증명하는 것**이 아니라, Cross-PVT feasible-island 연구를 수행할 수 있는 **최초 TT feasible point와 경계 부근 후보를 확보하는 것**이다.

EXP-002에서는 20 designs × 17 corners = 340 평가에서 feasible point가 0이었다.

Feasible island는 하나의 점이 아니라 **6개 target을 동시에 만족하는 설계 파라미터들의 연결 영역**이다. 따라서 데이터가 모두 infeasible이면 island topology를 직접 비교할 수 없다.

### 사용자가 확인한 평가 예산의 의미

`budget`은 돈이나 surrogate 예측 개수가 아니라 **실제로 TT SPICE로 평가하는 design point 수의 상한**이다.

```text
budget = 60
n_init = 20
adaptive ≤ 40

D000-D019: 초기 TT 평가
D020-D059: 적응형으로 고른 새 후보 최대 40개
```

초기 20개의 관측치로 한 번만 학습하는 것이 아니라, D020 결과를 얻으면 이를 포함해 다시 학습하고 D021을 제안한다.

50,000 candidate pool은 GP가 예측으로 screening하는 대상이며 50,000번의 SPICE 수행이 아니다.

`budget=60`은 EXP-002와 initial definition을 맞춘 pilot으로 선택했으며, 최적의 예산으로 입증된 값은 아니다.

### 왜 TT부터 평가하나?

Robust feasible design은 반드시 TT에서도 feasible해야 하므로, 우선 TT에서 joint-feasible 가능성이 높은 설계점을 찾는다.

그 뒤 가능성 높은 **여러 설계점**을 17-corner PVT로 평가한다.

하지만 TT feasible 자체가 robust feasible을 뜻하지 않으며, TT 점 하나를 찾는 것이 island 전체를 파악했다는 뜻도 아니다.

### 분석 및 기록 강화

단순 feasible count 외에 다음을 기록/해석한다.

- 7 design parameters
- 6 TT metrics
- iteration / phase
- spec 통과 개수
- normalized worst constraint margin
- total normalized violation
- ATLAS predicted topology diagnostic (`beta0`, `F_hat` 크기 등)

계획 그래프:

- iteration vs worst_margin
- iteration vs total_violation
- iteration vs spec별 normalized margin
- 필요 시 parameter trajectory와 ATLAS 내부 진단값

그 결과 first feasible을 찾지 못하더라도, trade-off 때문에 실패했는지 또는 실제로 경계에 가까워졌는지를 판단한다.

## 8. 별도의 TT Multi-Island Discovery 필요성 확인

### 문제 제기

TT에서 feasible point를 하나 발견해도, 그 주변만 탐색하면 **멀리 떨어진 다른 feasible island**를 놓칠 가능성이 있다.

예를 들어 TT에는 A/B 두 feasible region이 있고, 다른 corner에서 A는 사라지고 B만 남을 수도 있다.

현재로서는 **가설적 가능성**이며 해당 회로에서 이런 현상이 실제로 확인된 것은 아니다.

### 결정

- EXP-003: **최초 TT feasible point 발견** 및 adaptive trajectory 분석까지만 수행
- EXP-003에서 `early_stop=True`이므로 **다른 island 탐색은 수행하지 못함**
- 후속 단계: 다른 seed, global search, region별 boundary refinement, 필요 시 early-stop 없는 별도 run
- 실제 design space는 7D이므로, 2D 투영의 분리만으로 disconnected island라고 단정하지 않음

즉 연구 흐름을 다음과 같이 보강했다.

```text
EXP-003: first TT feasible discovery
→ TT multiple-island candidate discovery
→ 동일한 x 집합에서 17-corner SPICE
→ corner-wise feasible region / persistence
→ robust candidate selection 효율 비교
```

### 왜 동일한 x를 비교하나?

Corner별로 각각 다른 파라미터를 최적화하면 feasible 영역의 위치와 유지 여부를 직접 비교할 수 없다.

따라서 먼저 **같은 7개 parameter vector들**을 모든 corner에 반복 적용한다.

### 핵심 가설과 판정의 구별

metric별 worst-case compression은 **corner별 geometry / identity 정보**를 없앨 수 있으나, 모든 corner에서 정확히 worst metric을 계산했다면 **최종 robust feasibility의 참/거짓 자체는 보존**된다.

제안 방법의 가치는 더 정확한 pass/fail이 아니라, 이런 structure 정보로 **동일 simulation budget에서 robust design을 더 효율적으로 찾을 수 있는가**에 있다.

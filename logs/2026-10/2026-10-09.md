## 1. Important Correction — standard runner의 n_init은 고정 20이 아님

이전 EXP-002는 `TopoBO.optimize(...)`의 함수 기본값인:

```python
n_init=20
```

을 기준으로 `N_INIT = 20`을 명시적으로 사용했다.

그러나 실제 standard entry point인 `run_experiment.py`는 optimizer를 호출할 때 다음 함수로 `n_init`을 다시 계산한다.

```python
def n_init_for(evaluator, budget):
    return max(min(3 * evaluator.n_params, budget // 3, 50), 10)
```

two-stage GF180 op-amp는 design parameter가 7개이므로:

```text
3 × 7 = 21
```

budget이 63 이상이면 standard runner의 initial sample 수는 **21**이 된다.

예:

```text
budget = 500
→ min(21, 166, 50)
→ n_init = 21
```

따라서 EXP-002의 20-point dataset은 **TopoBO optimizer default n_init=20을 사용한 pilot**이라고 표현해야 하며, 일반적인 `run_experiment.py` 실행의 initial set과 완전히 동일하다고 표현하면 안 된다.

### 의미

EXP-002 결과 자체는 잘못된 것이 아니다.

20개 design × 17 PVT 결과는 그대로 유효하다.

수정해야 하는 것은 **baseline을 설명하는 표현**이다.

- EXP-002: optimizer-default `n_init=20` pilot
- standard runner: budget과 parameter 수에 따라 `n_init_for()`로 결정
- 7-parameter op-amp + budget >= 63이면 21 initial points

## 2. Initial 이후 Adaptive Loop 확인

`_GPBasedOptimizer.optimize()` 기준으로 initial evaluation이 끝난 뒤 각 iteration에서 다음 순서가 수행된다.

```text
observed X / metrics
→ working constraints 설정
→ surrogate fit
→ 50,000 candidate pool 생성
→ surrogate가 candidate metrics / feasibility 예측
→ near-feasible set F_hat 구성
→ Mapper topology 분석
→ wEI + topology term 계산
→ 최고 score candidate 1개 선택
→ 그 1개만 SPICE simulation
→ observation에 추가
→ 반복
```

50,000 candidates를 모두 SPICE simulation하는 것이 아니다.

surrogate로 50,000개를 저비용 screening한 뒤 **선택된 1개만 실제 simulation**한다.

## 3. Candidate Pool

현재 코드:

```python
N_CANDIDATES = 50000
```

아직 feasible point가 없으면:

```text
80% global LHS = 40,000
20% local      = 10,000
```

으로 구성한다.

local candidates는 현재까지 관측한 design 중 multi-spec score가 높은 최대 5개를 anchor로 사용한다.

feasible point가 생긴 뒤에는 global fraction이 60%로 감소한다.

---

## 4. Near-Feasible Set and Topology

ATLAS는 실제 feasible observation이 아직 없어도 surrogate prediction으로 near-feasible set `F_hat`을 만든다.

기본적으로 50,000 candidate 중 predicted feasibility score `h`가 높은 상위 약 10–20%를 선택한다.

그 뒤 Mapper를 이용해 predicted near-feasible region의 component / topology를 분석하고 candidate의 bridge / frontier / interior 역할을 acquisition에 반영한다.

따라서:

```text
actual feasible sample이 0개
≠
ATLAS가 topology를 전혀 사용할 수 없음
```

이다.

다만 **실제 corner-wise feasible island를 실험 데이터로 검증하는 것**은 여전히 실제 feasible / boundary samples가 필요하다.

## 5. Current 20 TT Data에서 발견한 추가 관찰

현재 D000-D019 TT 결과를 코드의 bottleneck 계산 방식에 대입하면, 각 metric은 서로 다른 design에서 이미 target을 한 번 이상 만족한다.

예:

- 어떤 design은 gain이 매우 좋음
- 다른 design은 phase margin이 매우 좋음
- 또 다른 design은 current가 매우 좋음

하지만 **하나의 design이 6개 spec을 동시에 만족한 경우는 없음**이다.

현재 코드의 bottleneck-aware weighting은 metric별 `best observed value`를 전체 design에서 각각 따로 찾는다.

그 결과 첫 adaptive step에서 UGBW가 상대적으로 가장 큰 bottleneck weight를 받고, phase margin은 다른 design에서 높은 값이 이미 관측되었기 때문에 큰 bottleneck으로 보지 않는다.

반면 실제 near-feasible TT designs인 D000 / D007 / D008 / D009는 모두 **phase margin 하나 때문에 infeasible**하다.

### Interpretation

이 관찰은 흥미롭지만 아직 “ATLAS가 잘못됐다”고 결론 내릴 수 없다.

이유:

- bottleneck weighting은 acquisition의 일부일 뿐이다.
- `compute_h()`, probability of feasibility, Mapper topology는 여러 spec의 joint structure를 함께 본다.
- 실제 adaptive trajectory를 확인해야 이 weighting이 candidate selection에 어떤 영향을 주는지 판단할 수 있다.

따라서 다음 실험에서 확인할 핵심은:

> **D020 이후 adaptive candidates가 실제로 joint-feasible direction으로 이동하는가?**

이다.
